UI test runner for Android, iOS and the web

Test Buddy (tb) runs Maestro-compatible YAML flows on Android, iOS simulators and Chrome. It waits on events from the device instead of polling the screen. One flow can drive several devices, and the same commands work from a shell for AI agents.

Features

What it does

Maestro-compatible

Every command, selector and condition, runFlow, repeat, retry, JavaScript, env rules, config.yaml, tags and JUnit/HTML reports, with the same command-line options. Point tb test at your .maestro folder.

Event-driven waits

The on-device agents push "the UI changed" and "the UI settled" events, and tb waits on those. A screen is read again only after the device says it changed. Spinners and tickers that never stop are marked restless and stop holding the screen up.

Multi-device flows

Write one flow that drives an iPhone and an Android phone together, synced with signal and waitForSignal. Or spread a suite over devices with a work queue: --shard-split, --shard-all.

Shell commands for AI agents

tb look prints a screen in a few hundred tokens, tb do answers with what changed, and tb save turns the commands that worked into a flow. tb mcp serves the same commands as MCP tools.

Timeline and video reports

--timeline writes one HTML page per flow with every step, the screen before and after, and each tap drawn where it went. --record --annotate makes a captioned video to attach to a pull request.

Failure output

A failed step prints the screen as it was, with elements similar to what it looked for, and saves a screenshot, the hierarchy and a step-by-step log with times.

Static check of app code

tb a11y reads app source, with no device, and lists elements a test could not find or tap, in Android layouts, Compose, SwiftUI, UIKit, React Native, Flutter and web code. --fix adds the missing ids.

Web

CSS selectors, same- and cross-origin iframes, new tabs, mockNetwork to answer requests without a server, and answerDialogs and assertDialog for JavaScript dialogs.

Flow lint

tb check --lint lists steps that run but break easily: coordinate taps, match indexes, text that reads as a wider regex, flows that assert nothing. Flows saved by tb save are written without them.

How it works

How it waits

A runner can decide a screen is ready by reading it repeatedly, or by comparing screenshots until two match. Each step then costs several reads, and a screen that keeps moving never matches.

Test Buddy puts a small agent on the device (an in-page script on the web). It reports changes as they happen, so each step starts as soon as the app settles, and each tap waits for a still screen.

Benchmarks

Speed compared with WebdriverIO and Maestro

Each tool ran the same test on the same demo app: sign in, open and edit an item, scroll a list that loads more, and use screens that never stop moving. Seconds for the whole command, start-up included. Lower is better.

How it was measured

Each number is the mean (min–max) of 5 timed runs after a warm-up, one run at a time on one Mac on 2026-11-26, with each tool's defaults and the same 17 s element timeout. Versions: tb 0.7.0, Maestro 2.12.1, WebdriverIO 10.2.0 (through Appium 4.0.1 on Android and iOS). Other emulators and simulators were running on the Mac, so every tool's times are a little higher than on a quiet machine.

Why the web result differs

WebdriverIO clicks the moment an element is displayed, even while a screen is still sliding in. With a click recorder on the test page, 7 of its 120 runs clicked the wrong element, and 5 of those still reported a pass. tb waits for a still screen before each tap and never tapped during a slide-in. The same instrument caught a scrolling race in tb, fixed since: 0 wrong taps in the 15 runs after the fix.

Get started

Install and run

  1. 1

    Install tb

    curl -fsSL https://github.com/Elforama/testbuddy/releases/latest/download/tb_darwin_arm64.tar.gz | tar -xz
sudo mkdir -p /usr/local/bin && sudo mv tb_darwin_arm64/tb /usr/local/bin/
tb version

    Apple silicon. On an Intel Mac use tb_darwin_amd64.

    curl -fsSL https://github.com/Elforama/testbuddy/releases/latest/download/tb_linux_amd64.tar.gz | tar -xz
sudo mkdir -p /usr/local/bin && sudo mv tb_linux_amd64/tb /usr/local/bin/
tb version

    On Arm use tb_linux_arm64.

    Invoke-WebRequest https://github.com/Elforama/testbuddy/releases/latest/download/tb_windows_amd64.zip -OutFile tb.zip
Expand-Archive tb.zip -DestinationPath "$env:LOCALAPPDATA\Programs" -Force
$dir = "$env:LOCALAPPDATA\Programs\tb_windows_amd64"
[Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path", "User") + ";$dir", "User")

    PowerShell, Windows 10 or later. Open a new terminal, then tb version. On an Arm PC use tb_windows_arm64. Windows runs Android and web flows; iOS needs macOS and Xcode.

    go install github.com/elforama/testbuddy/cmd/tb@latest
tb version

    Go 1.27 or later. Keep the module path lowercase, and put $(go env GOPATH)/bin on your PATH.

    claude plugin marketplace add Elforama/testbuddy
claude plugin install test-buddy@test-buddy

    The tb CLI plus a tb skill for Claude. The bundled binary runs on Apple silicon Macs; elsewhere, install the CLI as well.

    Archives for every system, with SHA-256 sums, are on the latest release.

  2. 2

    Have a device ready

    AndroidAn emulator, or a phone with USB debugging. Needs adb.
    iOSA booted simulator on a Mac with Xcode.
    WebGoogle Chrome installed.
    tb devices    # what tb can drive, and which are free

    With no phone running, tb test -p android or -p ios starts an emulator or simulator for you.

  3. 3

    Write a flow and run it

    login.yaml 
    appId: com.example.app
---
- launchApp
- tapOn: "Email"
- inputText: "hello@example.com"
- tapOn: "Continue"
- assertVisible: "Welcome"

    tb test login.yaml -p android
tb test flows/ -p ios
tb test flows/ -p web --headless
tb check --lint flows/    # no device needed

AI agents

Driving a device from a shell

An agent opens a device, reads the screen as text with @refs, acts, and sees what changed. A background daemon keeps devices connected between calls. The commands that passed save as a flow you can replay in CI.

tb open -p android --app com.example.app
tb look                       # the screen, one line per element
tb do 'tapOn: @7' 'inputText: "hi"'
tb wait "Welcome"             # waits on device events
tb save flows/sign-in.yaml    # what worked, as a flow

Works with Claude Code (plugin), Codex, Gemini CLI, Cursor and GitHub Copilot through a portable skill. tb agent-guide prints a quick reference, and tb mcp serves MCP clients. Agent setup

Multi-device

Several devices in one flow

Give each device a role, run steps side by side, and hand off with signals. iOS, Android and web roles can mix in one file.

devices:
  alice: { platform: ios, appId: com.example.chat }
  bob: { platform: android, appId: com.example.chat }
---
- parallel:
    alice: [launchApp, { runFlow: login.yaml }]
    bob: [launchApp, { runFlow: login.yaml }]
- alice:
    - tapOn: "New message"
    - inputText: "Hi Bob"
    - tapOn: "Send"
    - signal: sent
- bob:
    - waitForSignal: sent
    - assertVisible: "Hi Bob"
